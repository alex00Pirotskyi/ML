# Mudra V6 — dual-objective Optuna student training

**Status:** experimental firmware-student training from V5 automatic (silver) TAP+SWIPE labels.

The V6 trainer and CI use the real, source-hash-verified DATA/DATA_TAP recordings, combine raw firmware features with V5 frame-aligned gesture labels, and export **ten independent candidate models as compact C headers with per-model JSON reports**.

## Objective / contract

- **Objective 1 — maximize**: confidence-weighted, subject-grouped F1 measured against V5 silver labels. There are three folds within the training group and an untouched subject-group outer test split.
- **Objective 2 — minimize**: compact static flash bytes from the existing export_plus LightGBM estimator, including tree tables, LUTs and early-exit bounds, not Python pickle size or source-header text size.
- **Binary target**: TAP or SWIPE = 1; FINGER, WRIST, ARM, BAND, NOTHING = 0. Unknown (-1) rows do not enter the loss. A separate gesture-kind classifier is necessary to distinguish TAP from SWIPE.
- **Firmware inputs**: 15 current EMG PSD values from CH1–CH3, optionally 3 waveform-length values, optionally 18 ACC PSD values. Only feature groups present in every recording can be selected; the model has no access to pointer, metronome, names, folder label, timestamps, or the V5 teacher's future features.
- **Anti-leakage**: exact timestamp alignment, original CSV SHA-256 binding, per-recording sampling, 22% subject-group outer holdout, three-fold participant-group CV. Trained full-data exports are scored on the holdout by a separate train-only fit, before full refitting.
- **Model selection**: ten distinct Optuna trials sampled across the F1 vs size Pareto frontier, with F1-maximizing and size-minimizing anchors, followed by balanced tradeoff selections.

## Exact files generated by each run

- Ten firmware C header files in results_v6/models, one for each selected Optuna trial, with a unique group name.
- Ten detailed JSON files alongside headers: Optuna hyperparameters/objective scores, per-fold metrics, held-out precision, recall, F1, ROC AUC, PR AUC, specificity/FPR, MCC, kappa, log-loss, Brier score, calibration error, per-gesture/subgroup hard negatives, event-witness coverage, feature selection/importance, static bytes and C smoke result.
- Ten feature-schema JSON files and corresponding pickle files for offline model reproduction.
- The entire study: optuna_study.sqlite3, optuna_trials.json, optuna_trials.csv, summary.json, experiment_manifest.json and dataset_manifest.json.

Reported size is exact **static generated model array bytes**, not total final nRF52832 ELF flash. C smoke compilation checks syntactic compatibility against a minimal stub t_core, not the actual firmware SDK. The export_plus Python representation parity validator also runs. Complete embedded C parity and cycle/RAM measurements are separate release gates.

## Reproduce from repository root

Install:

    python -m pip install numpy pandas scipy scikit-learn lightgbm optuna joblib

The workflow downloads the full, validated V5 label artifact from main-branch Actions run #43858013153. Preserve its nested results_v5_labels folder as in the archive, and run:

    python research/tap_real/test_train_optuna_student_v6.py

    python research/tap_real/train_optuna_student_v6.py \
        --input-dir DATA/DATA_TAP \
        --labels-dir research/tap_real/v5_cache/research/tap_real/results_v5_labels \
        --out-dir research/tap_real/results_v6 \
        --trials 40 --cv-folds 3 --top-k 10 \
        --max-per-class 45 --seed 20261116

Outputs must use a new, empty directory. Hash validation defaults on. Do not copy exported labels back into DATA/DATA_TAP.

## Interpretation

All F1, AUC and other reported scores are measured against **inferred V5 silver frame labels**. The original recording folders establish which gesture classes are present, but not the exact physical onsets. High pseudo-label agreement does not demonstrate true soft-tap recall, double-tap correctness, swipe specificity or real false-presses/hour. Before firmware deployment, compare selected candidates on independent recordings/participants, inspect the output C against real firmware core_type_def.h and check flash/RAM/CPU latency.

The ten candidates are a **quality–size tradeoff**, not ten supposedly independently certified production models.
