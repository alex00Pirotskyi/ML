# V5 → tiny binary LP model → Cortex-M4F (Optuna + export_plus)

**Purpose:** Build a field-test candidate for the Mudra/nRF52832 long-press release detector. The previous working **v20** model and firmware are unchanged. This pipeline generates **one binary classifier**, not nine simultaneous regressors: with a tap-gated LP, one release/hold probability is the lowest-risk embedded A/B experiment.

## One command (real full source corpus)

From repository root on the V5 Optuna branch:

```bash
git fetch origin
git switch research/lp-v5-optuna-embedded-20261116
python -m pip install numpy pandas scipy scikit-learn lightgbm joblib "optuna>=4,<5"
python train_lp_v5_optuna.py
```

Runs all **160 trials** by default, with no automatic early stop. Multiobjective **NSGA-II** explicitly maximizes participant-held-out V5 teacher-imitation score and minimizes **exact firmware static-array bytes** estimated by `export_plus.estimate_compact_tree_payload`. Final export is independently verified by `export_plus.export_to_c_header(validate=True)`.

### What gets trained

- **One binary LightGBM**: `lp_state=0` means active/holding and `lp_state=1` means resting/released, **positive classifier output is RELEASE = 1**.
- `lp_state=-1` is always excluded. Low-confidence control reference rest has its own reduced weight.
- Model input is **only raw firmware fields**:
  - `core18`: 3× `p_core->wl[CH]` and 15× `p_core->emg_psd_mean[CH][0..4]`.
  - `instant33`: core18 plus 15× `p_core->emg_psd[0][CH][0..4]`.
  - `full39`: instant33 plus 3× `p_core->wl_head[CH]` and 3× `p_core->wl_tail[CH]`.
- **No log/EMA/PSD-based runtime preprocessing** is required in the firmware. EMG PSD zones already carry firmware's log encoding; historic `psd_mean_applied` divided representations are corrected **in offline training only**.
- Feature subset (18/33/39), tree count/depth/leaves, learning rate, subsampling, L2 penalty and **0.05-increment Q20 rest threshold** are Optuna search parameters.
- **3-fold participant-held-out** validation. Optimized utility weights balanced accuracy and false release during pseudo-holds, while also retaining rest recall/F1; size is a separate Pareto objective.
- V5's partial-contact and noisy-pointer rules are respected: **one reliable channel is enough**, no pointer input to student, and unknown labels do not become negative examples.
- The generated header uses `export_plus.py` directly with `preprocessing="none"`, stable selected original feature indices and parity validation.

### Output directory

`LP_V5_EMBEDDED_OPTUNA/` is ignored by Git and contains:

| File | Purpose |
|---|---|
| `lp_v5_model.h` | **Cortex-M4F-compatible C model** generated by `export_plus.py` |
| `lp_v5_model.pkl` | Fitted Python LightGBM + selected-feature metadata |
| `lp_v5_feature_schema.json` | Original 39 firmware field names and selected indices |
| `lp_v5_model_info.json` | Threshold, Q20 integer, chosen model hyperparameters |
| `training_report.json` | Optuna score, fold metrics, exact static bytes, C parity, selected features |
| `optuna_trials.csv` | All trials and Pareto alternatives |
| `dataset_audit.json` | Counts, participant grouping, label provenance, weak contact-model CV |
| `pseudo_event_replay.json` | Full-rate **teacher-imitation**, 10-prediction trailing-Q20 smoothing on held-out LP recordings |

The size budget is **generated static data only**, excluding executable code, linker padding, stack, and BLE/IMU work. Python Optuna score and replay metrics are **not real-world physical accuracy**.

## Verified field-test candidate — 160 Optuna trials

[Successful full 160-trial GitHub Actions job](https://github.com/alex00Pirotskyi/ML/actions/runs/43907170437) generated and validated:

| Item | Result |
|---|---|
| Estimator | Binary LightGBM, release/rest = positive 1 |
| Trees | **32** (max depth 3) |
| Firmware inputs | **39** directly readable t_core fields |
| Exported static arrays | **3,172 bytes** (not including executable/stack/linker overhead) |
| Default release threshold | **0.55** (Q20=11) |
| Optuna CV utility | **0.83143** (weighted hold/BA/rest-F1 objective, **NOT accuracy**) |
| Export validation | **0** decision mismatches on 559 test inputs |
| C compilation | Passes host C11 compilation with a simulated t_core struct |

**Whole-rate held-out pseudo-label replay with the existing 10-probability average:** about **13.89% of V5 active/hold-labeled rows** still cross the resting threshold, while **68.91% of V5 resting-labeled rows** are detected. These are pseudo-label comparisons on held-out recordings, **not** measured real device rates; the replay does not include the actual tap-gated firmware state machine. Do not confuse the 0.831 score with 83.1% physical accuracy. In particular, watch for premature releases during sustained holds when you A/B test with v20.

The model is intentionally small enough to be practical for a controlled device trial, but **the true hold/release performance and real nRF52832 CPU/RAM cost remain unmeasured**.

## Embedded integration: only inside the existing tap-gated LP state

```c
#include "lp_v5_model.h"

// Call only after the existing tap model has already initiated a press.
// lp_state=1 is RELEASE/rest. Do not invert it!
float release_probability = lp_v5_predict_value(p_core); // Q20: 0.00, 0.05, ..., 1.00

// Keep your existing running average of the last 10 LP probabilities,
// hysteresis and release gating. Compare the average with the chosen
// decision_threshold from lp_v5_model_info.json for initial testing.
```

For **an unsmoothed** threshold test, `lp_v5_predict_q20(p_core, threshold_q20)` uses an exact raw-score comparison without `expf()`/`logf()`; `lp_v5_predict_value` returns a 0.05-quantized probability. For the firmware's existing **10-sample average**, average the Q20 float probabilities instead of averaging the 0/1 classification output.

The model header references `t_core` and `core_type_def.h`. The trainer compiles it against a minimal **host stub**, but **this is not proof it links into your actual firmware**. Compare generated feature names and `CH1/CH2/CH3` macros with your live firmware `t_core` before flashing. No firmware files are changed automatically.

**Initial test path:** save existing v20 firmware/export first; compile V5 header as a selectable A/B candidate; keep tap initiation unchanged; evaluate six familiar users + newcomers; track sustained-hold continuity, soft hold behavior, false release during a true hold, eventual release after physical relaxation, latency and MCU CPU/RAM/BLE metrics. If the new model is not demonstrably better, retain v20.

## Validation and safety caveats

- The V5 teacher used participant-out-of-fold weak contact quality to form labels. Those labels are NOT independent physical hold/force truth. CV measures **student imitation**, not real-event detection precision/recall.
- Grouping is based on historical `User` metadata or filename fallback, which may not uniquely identify people. Campaign/device holdout is not yet measured.
- The V5 labeler may abstain on some soft/steady holds; optimization cannot restore true events missing from the teacher.
- The full-rate replay compares to V5 *pseudo-labels*, not physical release time. It is not identical to the complete tap-gated firmware state machine.
- `lp_v5_predict_value` is intentionally a **single binary probability** to keep embedded footprint and integration simple. The nine offline quality/activity scores stay as research/training diagnostics and are not necessary for this first field test.
- Do not merge into production or replace the v20 baseline until firmware end-to-end tests pass.

## CPU usage and configuration (no CLI flags)

Both scripts automatically budget **80% of the CPUs available to the process**,
respecting CPU affinity and Linux cgroup CPU quotas.

- `lp_v5_labeler.py`: uses that number of **independent subprocesses** to label recordings in parallel; each worker limits BLAS/OpenMP threads to one.
- `train_lp_v5_optuna.py`: prepares training records in parallel with the same CPU budget, then gives the allocated threads to each sequential LightGBM Optuna trial (avoids trial-level oversubscription).
- This is an **approximately 80%-of-core-count budget**, not an exact measured 80% utilization or CPU throttle. On a single-core allocation it uses one core.
- To change the settings, edit `TrainConfig` or `LabelerConfig` **inside the Python files**. For example, set `cpu_fraction=0.60`, `trials=80`, or `max_static_bytes=16384` in `TrainConfig`. There are **no command-line switches**.

```bash
python lp_v5_labeler.py
python train_lp_v5_optuna.py
```

The labeler saves files only under `DATA/DATA_LONG_PRESS_LABELED_V5/`. It refuses to overwrite existing labeled recordings unless `LabelerConfig.overwrite=True` is explicitly selected in the script.

If the size budget is too restrictive, Optuna fails rather than silently exporting an oversized model.
